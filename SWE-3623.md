### 1.1 Basic Concepts

### 1.1.1 **Software-Intensive Systems** 
* Computer system
	* Combination of software and hardware 
* **Software-Intensive System** 
	* A computer system (software + hardware) combined with human activities 
	* A computer system that, when placed within its system of human activities, will affect the way people do that activity 
* "We will return to the theme of continuous change throughout the book" 

### 1.1.2 **Fitness for Purpose** 
* We can say a system is badly designed if it is not well suited to the purpose for which it was intended 
* We define _quality_ in terms of _fitness-for-purpose_ 
	* Meaning we cannot asses quality as a measure of software by itself 
	* We. An only assess quality when we consider the software in the context of a set of human activities 
* This all means that creating a quality piece of software requires knowing the software's purpose 

### 1.1.3 Complexity of Purpose 
* Because software-intensive systems involve a high degree of interaction between people, software and hardware, they are intrinsically complex 
	* i.e. computers have lots of buttons to press, many pixels to change, and a lot of processing 
* Consider control: human-computer interaction is _mixed-initiative_ - sometimes we tell the computer to do things, and sometimes it tells us to do things 
* _Situatedness_: sometimes the computer directly mediates between two people's activity; sometimes it's in the background recording something, etc. 
* **_Wicked Problems_**:
	* The term is clones by Ritter and Webber for problems with the following characteristics: 
		1. There is no definitive formulation of the problem - for example, because different stakeholders each have their own conception of what the problem is 
		2. There is no stopping rule - each solution is likely to lead to new insights into the problem, and the problem is never likely to be solved entirely 
		3. Solutions are not right or wrong, but merely better or worse 
		4. There is no objective test of how good a particular solution is - such a test involves the subjective judgment of various stakeholders 
		5. There is no pre-existing set of potential solutions, nor is there a well-described set of features of such solutions. These must be discovered during problem analysis 
		6. Every wicked problem is essentially unique - each problem is sufficiently complex that no other problem is exactly like it 
		7. Every wicked problem can be considered to be a symptom of another problem, which means it is hard to isolate the problem and hard to choose an appropriate level of abstraction to describe the problem 
		8. The designer has no 'right' to be wrong - because wicked problems often have strong political, ethical, or professional dimensions, stakeholders tend to be intolerant of any perceived mistakes by the designer 
	- The overriding feature of wicked problems is that arriving at an agreed statement of the problem _is_ the problem. Wicked problems are not just ill-defined; rather, they are the kinds of problems that tend to defy description 

### 1.1.4 Dealing with complexity 
* Requirements engineering offers a number of techniques for dealing with complexity of purpose. Of these, three general principles are so useful that we will briefly introduce them here 
* _Abstraction_: 
	* Abstraction involves ignoring the details so that we can see the big picture. When we take some set of human-computer activities and describe them as a system, we are using an abstraction. When we take two different actions and describe them as instances of the same general activity, we are using an abstraction 
* _Decomposition_: 
	* Decomposition involves breaking a set of phenomena into parts, so that we can study them independently. Such decompositions are never perfect, because of the coupling between the parts, but a good decomposition still offers us insights into how things work 
* _Projection_: 
	* Projection involves adopting a particular view or perspective, and describing only the aspects that are relevant to that perspective. Unlike decomposition, the perspectives are not intended to be independent in any way 

### 1.1.5 Defining Requirements Engineering 
* Requirements Engineering (RE) is a set of activities concerned with identifying and communicating the purpose of a software-intensive system, and the contexts in which it will be used. Hence, RE acts as the bridge between the real-world needs of users, customers, and other constituencies affected by a software system, and the capabilities and opportunities afforded by software-intensive technologies 
* The term "Requirements Engineering" is made of two unfortunate words

	* This view contends that system design cannot be reduced to a ration process because it always takes place in a complex organizational context

### 1.5 What do Requirements Analysts Do?
* Because of the variance surrounding Requirements and their systems/customers there is no 'one way' to do requirements engineering 
	* Still, there are specific techniques applied generally 
* Who? What? Where? When? Why? Which? How? 
	* Which problem needs to be solved? 
	* Where is the problem? 
	* Whose problem is it? 
	* Why does it need solving? 
	* How might a software system help? 
	* When does it need solving? 
	* What might prevent us from solving it?
